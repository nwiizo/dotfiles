# Reporting Discipline

実戦で「後から辻褄が合わない」事故を起こしやすいポイントの回避策。

## レポートファイルの命名・配置

以下は継続調査の配置例。依頼先の保存方針を優先し、調査の依頼だけで履歴ファイルや権限依頼書を増やさない。

- `docs/cost_analysis_YYYYMMDD.md` — 日付付きで前回版を残す。上書きは履歴を失うので禁止
- `output/<resource>_YYYYMMDD.json` — 生データを日付付きで保存、差分比較のベースライン
- `docs/<tracker>_history.md` — マイルストーン・完了施策を追記式で管理、1ファイルで全期間の進捗が見える
- 権限依頼用の IAM ポリシー JSON は `docs/*_additional_policy.json` として別ファイル化

## 削減額の表現規律

比較する期間と費用の定義を揃えた主指標を選ぶ。次の補助指標は、判断に必要なものだけ併記する：

- **月平均ベース** — 過去N ヶ月の平均との差。長期トレンド、外部共有時の基準
- **直前確定月との差** — 前回調査時点からの短期改善、担当者報告向け
- **月末換算（進行中の月）** — N日実績 × 30/N。推定値であることを明記

3つが食い違うのは正常（分母が違うため）。どれを主指標にするかを文脈で示す。

## 3段階優先度

- 🔴 **早期確認** — 未アタッチ・孤児などの候補。未使用という判定だけで変更・削除を許可せず、依存関係と所有者を確認する
- 🟡 **担当者確認要** — production タグ、外部連携、他チーム影響。1〜2ヶ月
- 🟢 **中期計画** — RI 満期待ち、移行完了待ち、アーキ変更伴うもの。3〜12ヶ月

既存の優先度区分があればそれを使う。判断材料が不足する候補は未確認とし、区分に合わせるために実施可能と断定しない。

## 重複計上の排除

類似施策が複数ある場合、対象リソースに重なりが出る：

- 孤児スナップショット、古い年代のスナップショット、`remove-before-` 命名のスナップショット → 同じスナップショットが複数施策の対象になる
- 停止 EC2 の EBS、停止 EC2 の EIP → 同じインスタンスに紐づく別リソース
- 未アタッチ EIP、停止 EC2 の EIP → 両方カウントすると二重計上

レポートで合計を出す前に：
1. 各施策の対象リソース ID を集合として確定
2. 集合の積（重複）を検出し、どちらか片方でカウント
3. 重複した数を「重複除外後」として明記
4. 実行時は集合の和で作業指示

## 警告・注記の必須項目

レポート作成時に以下のチェックが抜けがち：

- production タグのリソースに対する施策には「担当者確認必須」マーク
- 削除系施策には**実行順序の依存関係**（バックアップを親より先に削除しない等）
- RI 購入済みインスタンスのダウンサイズ提案には「RI 使用率低下」リスク
- RDS 削除時の `--final-db-snapshot-identifier` 推奨（スキップ指定がデフォルトの実装もある）

## 独立レビューで検出されやすい誤り

過去のレビューで発覚した典型的な誤り（自分でも起こす）：

- 同じ論点を2箇所に書いて矛盾（ある節では「適用可」、別節では「不可」）
- サマリの合計額が個別施策の合計と一致しない
- 優先度別集計の項目数と一覧表の行数が不一致
- 数値の単位（月額 vs 年額、ドル vs 円）混在
- 見かけ上の削減額と月末換算後の削減額を並列比較（分母不一致）

独立レビューが依頼または運用手順に含まれる場合は、上記の数値・対象・前提を確認する。判定ラベルだけで採否を決めず、指摘を実データと照合する。

## 履歴ファイルの更新規律

- マイルストーン一覧は追記のみ、過去データを編集しない
- 施策ステータスはチェックボックス式（⬜→✅）、完了日を必ず記入
- タイムラインに重要イベント（RI購入、大きなリリース、再分析）を追記
- 更新ログに誰が何を変更したかを記録（日付・主体・内容）

## 外部共有時の表現

- 金額は USD 原価 + 円換算（社内レビュー用）を併記
- パーセント削減率も付ける（絶対額だけでは規模感が伝わらない）
- 「既に実現した削減」と「今後の削減ポテンシャル」を明確に分離
- 前回調査との比較で「実施済み施策の効果」と「残施策のインパクト」を明示
