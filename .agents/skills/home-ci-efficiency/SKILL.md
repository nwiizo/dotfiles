# CIの待ち時間と実行量を改善する

利用者が早く結果を受け取れることと、計算資源の使用量が減ることを別々に確かめる。
既存のworkflow、言語、runner、検証範囲を出発点にし、計測できた原因へ小さな変更を加える。
調査依頼では提案まで、修正依頼では適用と検証まで進める。外部実行・投稿は既存の許可の範囲に従う。

## 何を減らすか決める

依頼と現在の構成から、対象workflow・イベント・コミット・runnerと、困っている結果を特定する。
合意済みの条件を聞き直さず、不明な値は不明のまま扱う。

| 見る値 | 判断すること |
| --- | --- |
| 結果までの経過時間 | 待機、実行開始、必要なチェックの完了までを区別する。並行jobの時間を足して算出しない。 |
| 総実行量 | jobごとの実行時間、runnerの種類、再試行を集計する。短い経過時間だけで使用量削減と判断しない。 |
| 信頼性 | 初回失敗、retry後の成功、キャンセル、レポート欠落を分ける。省略した検査を成功へ数えない。 |
| 費用 | 課金対象・無料枠・runner単価等が確認できた場合に計算する。実行分数だけで請求削減額を断定しない。 |

GitHub Actionsでは `.github/workflows/` のYAML、呼び出すスクリプト、lockfile、`needs` と
権限を読む。`rtk proxy gh run view <run-id> --json jobs` など、導入済みCLIのread-onlyな
取得手段を使う。組織のメトリクスにアクセスできなくても、得られるrun単位の証拠で進める。
ログに秘密情報が含まれ得るため、結論に必要な箇所だけを扱う。

## 観測から変更を選ぶ

- **後続を待たせる処理を探す。** workflowの依存関係とjob・stepの実測時間を対応させる。
  準備、build、test、転送のどこが支配的かを確かめ、原因の異なる遅延を同じ対策で直そうとしない。
- **キャッシュの有無を分ける。** 同じ入力、toolchain、features、runner、復元条件で比較する。
  hit率だけでなく復元・保存の時間も見る。キー不一致、対象の不足、権限、生成物の再利用可否を
  区別し、キャッシュがなくても正しい検証が完了する構成を保つ。
- **並列化の重複を数える。** setupとbuildの繰り返し、共有fixture・port・DBの競合、runner待ちを
  調べる。分割数は実測から選び、job内の並列処理とworkflowの並列jobを区別する。
- **Rustではコンパイルの内訳を見る。** 対象CIと同じprofile・features・targetで
  `rtk proxy cargo build --timings` を使えるか確認する。HTMLの依存関係と待ちを読み、
  不要なfeatureや同じcrateの重複buildを調べる。測定のためにユーザーのbuild成果物を消さない。
  warm buildをcold buildと比較せず、crate分割や依存削除を計測なしに勧めない。
- **失敗を見えるままにする。** テストが失敗しても必要なログを保存し、欠落した成果物は欠落として
  扱う。retry増加、`continue-on-error`、対象テストの削減で見かけの成功率を上げない。

キャッシュは再生成できる作業を省くため、artifactは実行結果を受け渡すために使う。
復元したキャッシュを信頼済みコードとみなさず、fork等の未確認コードへsecrets・書き込み権限を
渡さない。リリースやデプロイを途中で止めるconcurrency設定も、通常のPR検証とは別に判断する。

## 改善を確かめる

### 検証の基準を保つ

各必須チェックについて、守る動作、実際のコマンド、実行条件、失敗時に止める箇所を
対応させる。既存のworkflowと設定を使い、同じ基準を持つ文書やcheckerを重複して作らない。
ローカルの速い確認とCIの広い確認は、実測した費用と依存関係で配置する。
差分だけの確認で影響範囲を覆えない場合は、必要な共通処理・対応環境の検証を残す。

基準となる版との差分で、閾値、対象パス・features・matrix、skip、assertion、lint抑制、
例外設定も読む。移動・削除自体を禁止せず、以前検出できた重要な不具合を今も検出できるか、
代替チェックと具体例で確かめる。検証不足を速度改善と数えない。

新しい基準が必要なら、比較する入力・環境・測定方法とばらつきを先に揃える。
測定値と合否基準を区別し、単発の良い数値やノイズをそのまま新しい必須閾値にしない。
例外には対象、理由、代替確認、担当と見直す条件を残し、greenにするだけの恒久緩和を避ける。

### 同じ条件で効果を確認する

変更前に比較条件と、改善したと判断する値を固定する。まず一つの原因に対応する変更を行い、
manifest・workflowの既存検査と、成功・失敗・キャッシュなし等の関係する経路を確認する。
Actionやrunnerの仕様を変えるときは、使用バージョンに対応する公式資料を確認する。

同程度の実行を複数比較し、入力差やばらつきを記録する。一回の成功だけで改善を確定しない。
実runを起動できなければ、静的検査と期待する効果を示し、実測済みとはしない。
変更、根拠、経過時間・総実行量・信頼性への影響、残る制限を報告する。
採用判断は、効果と追加の保守負担を比べて行う。

## 判断の根拠を確認する資料

- 測定値の意味や取得範囲: [GitHub Actionsのメトリクス](https://docs.github.com/en/actions/concepts/metrics)。
- キャッシュとartifactの使い分け・信頼境界: [GitHubのキャッシュ解説](https://docs.github.com/en/actions/concepts/workflows-and-actions/dependency-caching)。
- Rustの待ち・並行処理・依存の見方: [Cargoのビルド時間レポート](https://doc.rust-lang.org/cargo/reference/timings.html)。

これらの資料を手がかりに、この環境のRust開発・コスト調査・最小変更の方針に合わせて設計した。
時間短縮と費用削減、テスト成功と検証範囲を別々に評価することを重視する。
