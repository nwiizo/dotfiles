# 利用者へ届く成果物を確認する

ビルドの成功、公開先への登録、利用者が使える状態を分けて確かめる。
既存のリリース手順と依頼範囲を優先し、準備の依頼では公開せず、公開まで許可済みなら
再承認を求めず進める。このスキルの選択だけでpublish・deployの許可を補わない。

## 検証したものと配布するものを揃える

- 対象repo、commit/tag、版、registry・環境、配布対象OS/architectureを特定する。
  必須チェックがその版と設定で実行されたか確認し、別のcommitのgreen CIで代用しない。
- source checkoutだけでなく、実際のarchive・crate・binary・imageの内容を確かめる。
  build後の再生成、同名artifactの混在、mutable tagによる差し替えがあれば同一性を確認し直す。
  既存のdigestや署名・来歴情報を使い、存在するだけで動作や安全性を保証すると扱わない。
- CLIは配布物からの起動、必要な同梱ファイル、主な操作、終了コードを対象環境で確認する。
  一時ディレクトリへ展開し、ホーム設定・認証情報を分離する。開発機のPATHにある別binaryや
  `target/`で作ったものの成功を、配布物の成功へ読み替えない。
- crateでは対象packageとregistryを指定した既存のpackaging手順を使う。
  `cargo publish --dry-run`はアップロードしない確認であり、公開完了の証拠にはしない。
  配布対象に含まれないローカルファイルやpath依存に頼っていないかも確認する。

## 戻せる範囲から展開方法を決める

変更前の動作へ戻す方法を、binary・設定、保存形式・DB、通信先・外部副作用に分ける。
旧版が新しいデータを読めるか、再実行が重複書き込みを起こさないかを確かめる。
Gitのrevertやfeature flagのOFFだけでデータまで戻るとは扱わない。復元時の損失範囲や
前進修正が必要な箇所を残し、確認のために実データを巻き戻さない。

段階展開が有効なら、対象群、見る操作・指標、継続・停止・復旧の条件を決める。
値は既存SLO、通常のばらつき、利用頻度、検知までの遅れから選び、固定の割合・待機時間を
一律に当てはめない。低頻度の処理や計測欠損を「エラー0なので成功」としない。
flagを使う場合は両状態を確認し、切戻しが不要になる条件と撤去担当を決める。
CLI配布へサービス向けのcanaryやflagを形式的に追加しない。

## 公開結果を確認する

公開操作がタイムアウトしても、失敗と即断して同じ操作を繰り返さない。
registry・release・deploymentの版と状態をread-onlyで調べ、登録済み、処理中、未公開、
観測不能を分ける。状態や重複時の動作が分からない間は再送せず、確認できる作業を続ける。

公開後は指定版の取得と影響する利用経路を確かめる。サービスのhealth応答だけで、
書き込み・読み戻し・非同期処理まで成功したとはしない。公開前検証、公開操作、公開後確認の
どこまで完了したかと、未確認の対象環境・動作を簡潔に報告する。

## 必要なときの参照

- Cargoの公開・dry-run・index反映待ち: [cargo publish](https://doc.rust-lang.org/cargo/commands/cargo-publish.html)（2026-10-27確認）。実行時は導入版と対象registryも確認する。
- Terraformの再作成・state・データ復旧が関係する場合は `home-terraform-change-review`、監視設計が必要なら `home-observability-design` の該当範囲を使う。
- 指示の由来を保守するときは[設計方針の参考資料](../../docs/engineering-sources.md)を読む。
