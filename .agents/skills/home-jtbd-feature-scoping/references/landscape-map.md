# 簡易マップと判断の理由

As-Isの流れとマップは別の問いに答える。混ぜると、横軸を作業順と読み違えたり、
マップを構成図のように細かく描いたりする。

| 図 | 答える問い |
|---|---|
| As-Isの流れ | 何がどの順に起き、どこで待ち・戻り・迷ったか |
| 簡易マップ | 何が何を必要とし、それぞれがどの程度確立しているか |

## 書式

縦はユーザーからの見えやすさ、横は進化の段階。テキストで描くときは木構造で依存を示し、
各要素の後ろに段階と依存の種類を書く。不明な位置や依存には `?` を付ける。

```text
障害対応の担当者（夜間、一人で一次対応）
└─ 影響を受けた利用者の範囲を短時間で把握したい
   ├─ 影響範囲を10分以内に特定できる
   │  └─ 影響範囲の集計画面 [固有に作る]
   │     ├─ リクエストログ [共通基盤] 仕組み
   │     └─ 顧客と契約の対応表 [固有に作る?] 知識: 営業だけが更新
   └─ 誤った相手へ連絡しない
      └─ 連絡先の一覧 [既存製品から選べる] 順番: 契約更新後に反映
```

この例では、集計画面を足しても対応表の更新が営業の手作業に依存する限り、
特定の速さは対応表の鮮度で止まる。最初の確認は画面の作成ではなく、
対応表を一次対応で使える鮮度に保てるかになる。

## 進化の段階と扱い

| 段階 | 判断の問い | 扱い |
|---|---|---|
| 探索中 | まだ形がなく、試しながら探すものか | 小さな実験で学ぶ |
| 固有に作る | このサービスの事情に合わせる価値があるか | 中心のニーズに限って作り込む |
| 既存製品から選べる | 比べて選べる製品やサービスがあるか | 比較して使う |
| 共通基盤 | 当たり前の基盤として利用できるか | 独自に作らず安定して使う |

## 判断と理由の印

| 判断 | 見分け方 | 理由の印 |
|---|---|---|
| 今回は外す | スコープの外、またはジョブ・ニーズまで線をたどれない | 範囲外／ジョブにつながらない |
| 後の候補へ移す | ジョブには関係するが、最大の制約を変えない | 制約に効かない |
| 減らして残す | 情報や選択肢が増え、目的の行動までの判断が増える | 迷いを増やす |
| 小さな案へ戻す | 多くのデータ、知識、順番の調整が必要 | 支えにくい |
| 既存のものを使う | 同じ役割を果たす既存の道具やサービスがある | すでにある |
| 小さく試す | 中心のニーズを助け、短期間で反応を得られる | 試して確かめる |
| 維持する | ニーズと制約に働き、支え続けられている | 根拠の段階を併記 |
| 削除候補 | 既存機能だが対応するニーズがない、または重複している | 利用実態と移行の確認手順を併記 |
