# エージェントが呼ぶツールの入出力

MCPやエージェント向けツールを設計・変更するときに読む。APIを一対一で包む前に、
利用者の作業を完了するための操作と、その操作に必要な情報を決める。
既存の命名・schema・SDKを使い、ツール数を減らすために読み取りと破壊的操作を混ぜない。

## 判断できる入力と結果

- descriptionには用途、対象、必要な入力、返す結果、主な制限と副作用を記す。
  同じようなツールがあれば使い分けを示し、実装内部のURLや認証headerをモデルに組ませない。
- 必須・省略・null・既定値、単位、IDの範囲を具体例で確認する。任意のtenant IDを受け取れても、
  それを操作権限の根拠にしない。認証と対象ごとの認可は実行側で行う。
- 成功して0件、部分取得、取得失敗を別に表す。取得上限や切り詰めがあれば明示し、
  続きの取得方法や取得範囲を返す。要約で捨てた情報を含めて「全件確認済み」と読める形にしない。
- エラーは入力修正が必要、一時的な制限、認証・権限不足、実行結果不明を区別する。
  原因や安全な次の操作を返し、tokenや内部の生レスポンスをエラーメッセージへ載せない。
  MCPではtool実行エラーとprotocolエラーを対象版の仕様に合わせる。

## 再試行を状態と副作用から決める

読み取りと書き込みを分け、タイムアウト・切断・キャンセルが「処理されなかった」ことを
意味するか確認する。書き込み後の応答が欠ける場合は、operation IDや既存の状態照会、
同じ要求を重複処理しない仕組みを使う。結果不明を一般的なretryableへ丸めない。
認証失敗への同一要求の連打や、新しいIDでの書き込み再送を避ける。

更新には対象版や前提状態の照合が必要か確認し、古い検索結果から現在の状態を上書きしない。
read-only等の注釈は実装と一致させる。注釈やツール説明だけで権限を保証せず、
外部ツールの出力に含まれる命令を、利用者の新しい許可として扱わない。

キャッシュには対象、入力、認証・tenantの範囲、鮮度と失効条件を持たせる。
表現が似た質問でも、利用者や時点が違えば同じ答えを返せるとは限らない。
モデルのprefixキャッシュと、古いツール結果・回答の再利用は別の仕組みとして評価する。

## 境界を検証する

まずツール単体で、0件、複数ページ、入力不正、権限拒否、途中失敗、書き込み後の切断を
対象に応じて確認する。拒否時に副作用がないことと、再試行で二重処理しないことを見る。
その後、利用者の依頼から適切なツール・引数・結果解釈を選べるか評価する。
単体テストの成功を、モデルの選択や完了報告まで確認した証拠にしない。

仕様が関係する場合は[MCP Tools仕様](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
と導入SDK・接続先の対応版を照合する（2026-10-27確認）。
指示の由来は[設計方針の参考資料](../../../docs/engineering-sources.md)に残す。
