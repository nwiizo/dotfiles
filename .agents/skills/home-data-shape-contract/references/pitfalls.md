# データ境界の確認事項

対象の形式に関係する項目だけ確認する。既存の仕様と利用側の動作を優先する。

- **null・欠損・空:** 意味が異なるなら区別を保持する。部分更新では「変更しない」と
  「値を消す」の表現を明確にし、実際の serializer/deserializer で往復を確認する。
- **時刻:** 発生時点、日付、現地時刻での予定を区別する。epoch は単位を明示する。
  予定の意味に時間帯が必要なら、UTC オフセットだけで足りるか確認する。
- **数値:** 金額・通貨・割合・単位・丸め方法を明確にする。大きな整数を JSON で渡す
  場合は利用側の精度も確認し、必要なら文字列など損失のない表現を選ぶ。
- **識別子:** 公開範囲と推測可能性を考慮する。ID の形式をアクセス制御の代わりにせず、
  既存 ID の意味や表現を都合だけで変えない。
- **未知値:** フィールド追加、enum 追加、optional 化を一律に安全と扱わない。
  古い reader と新しい writer、その逆の組み合わせを確認する。
- **移行:** 読み側と書き側の更新順、既存データ、段階展開、ロールバックを考える。
  format version や二重書きは、その運用が必要な場合に導入する。
- **一覧とエラー:** ページング・メタ情報・機械向けエラー識別子は現在の用途に合わせる。
  将来の可能性だけで全出力をラップしたり、新しい共通形式を追加したりしない。

フレームワーク固有の属性・型・既定値は導入済みの版と公式資料で確認する。
型定義だけから、未知フィールドの扱いや保存済みデータとの互換性を断定しない。
