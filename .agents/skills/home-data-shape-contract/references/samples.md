# データ形式の判断例

違いを説明する必要があるときに使う例。形式・行数・確認手順を固定するテンプレートではない。
before/after と読み書きへの影響を、判断に必要な範囲で示す。

## 既存設定値だけを変える

```json
{ "telemetry": true }
```

依頼が「telemetry を false にして」なら同じキーの値を変える。
データ構造の再設計や追加の合意は不要。設定を読むアプリの検証方法で確認する。

## 状態を独立した軸に分ける

```json
{ "status": "active_trial" }
```

独立に変化することが要件から確認できるなら、次が候補になる。

```json
{ "lifecycle": "active", "plan": "trial" }
```

既存の `status` を置き換えると旧クライアントに影響する。
追加フィールドを旧クライアントが受け入れるか確認し、読み書きの切替順序を決める。
独立でない軸を分けると不可能な状態が増えるので、名前だけで分割を決めない。

## 大量の機械向けデータ

```json
{ "series": [
  { "timestamp": 1738368000, "value": 42.5 },
  { "timestamp": 1738368060, "value": 43.1 }
] }
```

容量や処理量が問題になる場合は列形式も候補になる。

```json
{ "cols": ["timestamp", "value"],
  "rows": [[1738368000, 42.5], [1738368060, 43.1]] }
```

代表データで差を測り、読み込み側の変更と運用負担も比較する。
新規でも実装コストはあり、公開済みなら移行が必要。
人が編集する設定を、この例だけを理由に列形式へ変えない。
