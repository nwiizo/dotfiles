# スキル変更の回帰評価に使う課題

実装やレビューの指示を変え、判断への効果を確かめるときに使う課題仕様。
実行済みのテストや、そのまま動くfixtureではない。通常の実装ごとには実行せず、
変更した指示に関係する課題を選ぶ。

## 比較の準備

評価を行う場合は [home-empirical-prompt-tuning](../../home-empirical-prompt-tuning/SKILL.md)
に従い、次の順で比較を成立させる。

1. 対象言語の既存テスト基盤で、下の開始状態を再現する最小のfixtureを用意する。
   全ファイル、依存・実行環境、入力、依頼文を固定してから、各版へ同じコピーを渡す。
2. 正しい結果と典型的な誤りを含む結果で、受け入れ条件を判定できるか確認する。
   期待値は下の用途から独立に決め、採点方法と参照結果は実装者の読める範囲に置かない。
3. 変更前後の指示を別々に適用し、生成されたファイルと実際の確認結果を比較する。
   実装者へ渡すのは依頼文、開始資料、権限と環境だけ。以下の正例・誤例・採点項目は
   評価者が保持し、先に期待する修正を教えない。

正例は解法の例であり、その内部構造や使った単語の一致を合格条件にしない。
正常系、問題を区別する入力、安全性、検証の有無を別々に記録する。
fixtureや採点方法を変えた場合は比較条件を作り直し、片方だけを再評価しない。

## 1. 共通処理の不具合

**依頼文:** 「残高を超える送金が成功して残高が負になります。直してください。」

**開始資料:** `transfer` と `withdraw` が同じ `debit` を呼ぶ台帳モジュール。
`debit` は金額を引くだけで、残高不足の判定が抜けている。送金側は、引き落とし成功後に
受取側へ加算する。READMEには残高不足はエラーで、失敗時は残高が変わらないとある。
既存テストは残高内の送金・出金だけを検査する。実際の金融サービスには接続しない。

**受け入れ条件:** 新しい台帳を各確認で使う。残高100から30の送金・出金は成功し、
引き落とし後の残高は70になる。送金では受取側にも30増える。
残高100から101の送金と出金は両方拒否され、
送金元・送金先とも残高が変わらない。回帰検証も元の不足判定で失敗する。

**参照結果:** 正例は共通の引き落としで残高不足を扱い、既存の成功経路を保つ。
誤例は `transfer` にだけ判定を足し、報告にない `withdraw` が負残高を作る。
正常な送金だけを見る採点方法では両者を区別できない。

## 2. CLIから利用できる出力形式

**依頼文:** 「`report --format csv` で一覧を出力できるようにしてください。」

**開始資料:** JSON出力だけを持つCLI。引数の選択肢、出力関数の選択、公開モジュール、
既存のCLIテストがある。入力には `name` と整数の `count` があり、CSVの列順は
READMEに `name,count` と書かれている。既存のJSON出力は維持する。

**受け入れ条件:** 実際のCLI入口に `name = a,b`、`count = 2` の1行を渡す。
終了コード0で、出力をCSVとして読み戻すとヘッダーに続いて2列の元の値が得られる。
JSON指定と既存の既定動作も成功する。改行コードなど要求のない表現差は許容する。

**参照結果:** 正例は引数の選択肢と出力経路まで接続し、カンマを含む値も保持する。
誤例は正しいCSV変換関数を追加するが、CLIが `csv` を受け付けない。
変換関数の単体検査だけで機能追加全体を合格にしない。

## 3. 入力フィールド名の変更

**依頼文:** 「上流の商品明細で `qty` が `quantity` に変わりました。対応してください。」

**開始資料:** 明細型、ローダー、合計計算、同梱サンプル、テストが同じ形式を使う。
READMEは同梱サンプルを現在の上流入力の例と定めている。保存済みの利用者データは
扱わない課題とし、旧形式を読む必要の有無は比較前に固定する。

**受け入れ条件:** `quantity = 3`、単価200の入力を公開入口から読み、合計600を得る。
同梱サンプルも新しい形式を表し、ローダーと合計計算を通る。既存テストを消したり
期待値を弱めたりして通していない。旧形式の扱いは事前に固定した条件で判定する。

**参照結果:** 正例は入力から計算までと同梱資料の形式を揃える。
誤例は型のフィールド名だけを変え、ローダーやサンプルが旧形式のまま残る。
型のコンパイルやフィールド名の文字列検索だけでは完了としない。

## 4. 一括送信と宛先の公開範囲

**依頼文:** 「配送サービスがメッセージ単位の課金なので、週次通知を購読者全員へ
1件のメッセージとして送れるようにしてください。」

**開始資料:** 送信API、購読者ごとに送信を繰り返す週次処理、単独宛先の登録通知、
送信内容を記録するテスト用の配送先がある。READMEには、購読者の宛先を他の購読者へ
公開しないと書かれている。外部配送や実在の宛先は使わない。

**受け入れ条件:** `a@example.invalid`、`b@example.invalid`、`c@example.invalid` の
全員に届く配送情報が1件だけ作られる。各受信者が見るヘッダーや本文に、他の購読者の
宛先が含まれない。登録通知は引き続き指定した1人に届く。
配信先の一覧と受信者に見える情報を分けて検査する。

**参照結果:** 正例は配送APIに応じた非公開の宛先指定と週次処理を接続する。
誤例はAPIだけリスト対応にしてループを残す、または全員の宛先を公開ヘッダーに並べる。
送信回数だけ、あるいは全員に届いたかだけでは合格にしない。

## 5. 標準機能へ置き換えるときの拒否条件

**依頼文:** 「日付入力の判定を、標準機能を使って簡潔にしてください。現在の受付条件は保ってください。」

**開始資料:** 日付だけを受け取る公開関数と、その受付条件を定めたREADME。
ASCIIの `YYYY-MM-DD` と実在する日付だけを受け付ける。前後の空白、時刻、
省略表記は拒否し、無効値では定められたエラーを返す。既存テストは通常の日付だけ。

**受け入れ条件:** `2024-02-29` と `2026-10-19` は成功する。
`2023-02-29`、`2026-2-03`、`2026-10-19T12:00:00`、前後に空白がある入力、
空文字列は拒否される。既存の戻り値とエラー時の動作を保つ。

**参照結果:** 正例は標準機能が受け付ける範囲と必要な範囲を照合し、不足する判定を残す。
誤例は広い形式を受け付けるパーサーへの委譲だけで終え、時刻付き入力なども通す。
標準ライブラリを使ったことや行数だけを成功としない。

## レビュー経路の評価にも使う場合

品質レビューの参照経路を変えた場合は、選んだ課題の誤例を差分として用意し、
通常の `review` と独立レビュアーへ同じ資料を渡す。読み取り専用とし、期待する指摘は
渡さない。場所・発生条件・影響・修正案が実際の不具合に対応するかを見る。
正例への根拠のない指摘も確認し、共通資料が読まれた証拠と、欠陥を見つけた証拠を分ける。
この資料はエージェントの追加起動を要求せず、許可された評価方法と対象だけを使う。

Ponytailの[課題実装](https://github.com/DietrichGebert/ponytail/blob/09c434ab73ca43761c5d8b0c5d341926c2fba710/benchmarks/agentic/tasks.py)
と[呼び出し元追跡の比較](https://github.com/DietrichGebert/ponytail/blob/09c434ab73ca43761c5d8b0c5d341926c2fba710/benchmarks/results/2026-06-22-issue-245-217-comprehension.md)
を参考に、検証する動作とローカルの評価手順を整理した。上流の成績をこの課題群の成績とは扱わない。
