# CLIと自動処理の入力・操作権限

外部入力からコマンド、ファイルの削除・上書き、認証付き操作へ進む処理の実装・レビューで読む。
形式が正しい値と、その操作に使ってよい値を区別する。一般的な文言修正へ監査を追加しない。

## 値を書いた主体から信頼を判断する

入力元、値を変更できる主体、動く権限、失われるものを一つの処理経路として追う。
OSから読んだ他プロセスの引数、設定、共有ボリューム上の名前、job payload、LLMの出力も、
第三者が書けるなら信頼済みにはならない。認証済みでも対象resourceへの操作権限は別に確認する。

文字列をshellへ組み立てず、既存の構造化引数APIを使う。Rustの`Command::arg`でも、
呼び出すプログラムによるオプション解釈や`sh -c`等の再解釈までは防げない。
実行先、引数の許可範囲、`--`の対応、環境変数と作業ディレクトリを対象ツールに合わせて確認する。
LLMの提案を実行するときも、プロンプトの注意書きで操作権限の検証を代用しない。

## 自動クリーンアップを狭い範囲に閉じる

- 削除対象は、管理側が保持する作業ID等から必要な範囲へ対応させる。
  payloadが渡す絶対パスや深さの確認だけで、削除してよいとは判断しない。
- 許可した管理ディレクトリの配下にあることと、管理ディレクトリ自体ではないことを確認する。
  文字列のprefix比較ではなく、パス成分とsymlinkの解決・扱いを実際のAPIに合わせて考える。
  解決失敗や所有情報の欠落で、親ディレクトリや既定パスへ処理範囲を広げない。
- 対象内のmarkerは、対象へ書ける相手も作れる。所有の証拠は信頼できる管理情報と照合し、
  片付けで証拠を消す前に確かめる。拒否や失敗のログへ秘密値を含むpayload全体を出さない。
- パス確認後に第三者が親や対象を差し替えられるか調べる。`canonicalize`を呼んだだけで
  確認から操作までの競合がなくなるとは扱わない。既存APIの保護と対応OSを確認し、
  必要ならディレクトリの変更権限やhandleを使う方式で範囲を固定する。
  symlink自体を外す処理では、解決先を消す変更を加えない。

検証には専用の一時ディレクトリを使い、正常な対象が処理されることと、対象外の目印ファイルが
残ることを確認する。管理rootそのもの、外部を指すsymlink、偽marker、情報欠落、途中失敗から
実装に関係する例を選ぶ。実ホームや認証領域を試験対象にしない。

依存の監査では、既知のアドバイザリがないことと、取得元や実行されるbuild script等を
信頼できることを分ける。対応OS・featuresとbuild/test/deploy経路の到達性を調べ、
保留には根拠と見直す条件を残す。未調査を「到達不能」と扱わない。
