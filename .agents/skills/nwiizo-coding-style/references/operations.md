# 操作ごとの手順

依頼された操作の部分だけを使う。`review`、`audit`、`debt`、`gain`、`help` は
現在の継続モードを変えない。`off` でも明示された操作だけは実行する。

## review: 差分レビュー

指定された未コミット差分、staged差分、コミット、ブランチ、PR、ファイルを読む。
ブランチやPRでは比較元を確認し、対象と無関係なローカル変更を混ぜない。
対象がなければ staged / unstaged の差分と untracked の新規ファイルを確認する。
新規ファイルは `git diff` に出ないため実物を読む。未コミット変更がなければ、
直近コミットを対象にしたことを明示して読む。履歴もなければ対象がないと伝える。

```bash
rtk git status --short
rtk git diff
rtk git diff --cached
rtk proxy git ls-files --others --exclude-standard
```

[review-checks.md](review-checks.md) を読み、処理の流れ、想定負荷、全確認観点、
指摘の裏付けに使う。独立した品質レビューと同じ資料を参照する。
Rust では [rust-analysis.md](rust-analysis.md) の両CLIによる診断を加える。

### 報告

対象の変更が利用者に何をもたらすかと、修正の要否を先に短く示す。
指摘は重要度順に番号を付ける。分類は「要修正」（不具合、安全性、データ損失、
想定負荷で破綻）、「改善推奨」（危険な処理の検証不足、実害のある遅延、重複、
責務の混在、不要な処理）、「任意」（小さな高速化や読みやすさ）を目安にし、
該当しない分類は省く。明示された出力形式があればそちらを使う。

共通資料の指摘内容に種別を添え、初見の読者にも分かる言葉で説明する。
必要な専門語は補い、修正を優先する番号と調べた範囲・想定負荷を明らかにする。

削減可能な行数や依存数を出す場合は、具体的な差分または置換案から数え、見込みと
実際の変更を区別する。根拠がなければ数値を出さない。
レビューのみなら指摘で終え、修正も依頼されていれば適用と検証まで行う。

## audit: 全体監査

対象は指定されたリポジトリかディレクトリ。省略時は現在のリポジトリを使う。
管理対象のソースと依存定義を調べ、生成物、外部依存のコピー、ビルド出力を除く。
README、デプロイ・ビルド設定、依存、エントリーポイント（main、route、handler、job、
CLIコマンド）、テストから構造と想定負荷を把握する。

主要な入力・保存・出力の経路を一通り読み、ユーザー入力、金額、認証、書き込み、
バックグラウンド処理、プロセス間共有を重点的に追う。大きい対象では、誤りの影響が
大きい経路を優先して深く調べ、読めなかった領域を明示する。

[review-checks.md](review-checks.md) の全観点・裏付けと、`review` の報告方法を使う。
差分の有無にかかわらず、既存の危険な処理の検証不足や、複数箇所で異なる規則を
適用している問題も確認する。
Rust では両CLIを使い、実際の解析範囲を確認して重複実行を避ける。
報告では対象の役割と想定負荷を示し、利用者への影響、起きる条件、保守負担から
優先順を付ける。推測の削減行数だけでは順位を決めない。
指摘が多い場合は領域や重要度で整理し、件数の上限を理由に重要な問題を隠さない。
監査のみなら指摘で終え、改善の実行も依頼されていれば指定範囲で適用・検証する。

## debt: 残した制限の一覧

コードに残した次のコメントを検索する。Ponytailの `shortcut:` と旧形式の
`ponytail:` も含める。依存・生成物に加え、リポジトリのignore設定に従う。

```bash
rtk proxy rg -n --hidden --glob '!.git/**' --glob '!node_modules/**' --glob '!vendor/**' --glob '!target/**' --glob '!dist/**' --glob '!build/**' '(nwiizo-coding-style|shortcut|ponytail):' <対象>
```

別のマーカーを指定された場合は、その語を固定文字列として検索する。
ヒットの周辺を読み、実際に制限を残したソースコメントだけを抽出する。
説明文、文字列中の例、キーボードショートカットの説明などは集計しない。
検索の終了コード1は該当なし、2は実行失敗として扱う。言語固有のコメントも考慮する。

ファイル・行、残した制限、見直す条件、対応をファイルごとに一覧化する。
見直す条件が書かれていないものには `no-trigger` を付け、推測で補わない。
最後に実際の件数と `no-trigger` の件数を示す。0件なら対象範囲で該当なしと伝える。
必要なら `git blame` で変更者を調べられるが、変更者を今の担当者とは決めつけない。

保存も依頼されていれば指定先かリポジトリの既存の課題管理文書に書く。
明示された保存依頼にもう一度承認を求めない。報告だけの依頼ではファイルを増やさない。

## gain: 効果表示

公開ベンチマークのスコアを、対象モデル、課題数、反復回数、測定日と一緒に表示する。
起点は [2026-10-07 の公開結果](https://github.com/DietrichGebert/ponytail/blob/09c434ab73ca43761c5d8b0c5d341926c2fba710/benchmarks/results/2026-10-07-agentic.md)。
最新値を求められた場合は、上流の新しい一次資料を確認する。
Claude Code CLI 2.1.288、Opus 5.5、default effort、39課題・各5回で、
Ponytail 5と同じエージェントのスキルなしを比較している。
削減率は課題ごとの中央値の比を幾何平均したもの。

| スキルなしとの比較 | 公開値 |
|---|---:|
| 提出コードの行数（コメントを含み、テストを除く） | −53% |
| 出力トークン数 | −45% |
| 費用 | −26% |
| 所要時間 | −41% |

品質の値を併記する場合は、非公開の動作検査が87/90件合格（スキルなし86/90件）、
テストが必要と分類された課題で検証を残した割合が98%（同68%）であることを示す。

これはPonytailの作者による測定であり、`nwiizo-coding-style` や現在のリポジトリの
効果ではない。旧版・別モデルの結果と混ぜず、Codexなど別の実行環境へ一般化しない。
生成時のBashは無効で、検証は後から実施した測定。動作の非公開検査は18課題だけで、
残り21課題の提出・コンパイルやモデルによる完全性の評価を動作保証に読み替えない。
プライバシー課題は各群2/5回しか合格しておらず、テストを残す割合と不具合を検出する
能力も別の指標である。結果を一般的な正しさ・安全性の保証として表示しない。

手元の効果を求められた場合は、指定された変更前後で確認できる差分、依存数、
診断結果を示す。実測していないトークン・費用・速度や、作らなかったコードの量は
推定しない。コードが小さくなったことだけで動作の同等性を判断しない。
表や短い棒グラフは比較を助ける場合に使い、状態やモードは変更しない。

## help: 使い方

現在モードと既定値を確認し、`SKILL.md` の操作表に沿って説明する。
必要な操作が分かっていれば、その呼び出し例だけを示す。

```text
$nwiizo-coding-style full この処理を実装して
$nwiizo-coding-style review
$nwiizo-coding-style audit crates/parser
$nwiizo-coding-style debt
$nwiizo-coding-style gain
$nwiizo-coding-style default lite
$nwiizo-coding-style off
```

これはスキルの会話上の操作であり、同名のシェルコマンドではない。
モードは会話内で引き継ぎ、新しい会話では環境変数または文書の既定値に戻る。
開始時や子エージェント起動時の外部フックが動作しているとは説明しない。
