# 品質レビューの確認観点

`review`、`audit`、独立した品質レビューで共通に使う。
対象範囲、編集・実行権限、専門診断の起動条件、報告形式は呼び出し元に従う。
この資料を読むだけでモードを変えたり、追加のツール実行を許可されたと扱ったりしない。

## 処理の流れと想定負荷

差分に加え、変更された関数の呼び出し元・呼び出し先、テスト、fixture、README、
関連設定を読む。入力、保存、出力まで追い、シグネチャ・戻り値・動作の変更が
差分外の利用箇所を壊さないか検索する。共通処理の不具合を呼び出し元だけで
回避していないかも確認する。

READMEやデプロイ設定から、単独で動くCLIか、複数利用者・プロセスが同時に使う
サービスか、入力件数やデータ量はどの程度かを確認する。根拠と仮定を区別して示す。
不明な大規模負荷を想像して設計を増やさず、判断を左右する未確認事項として残す。

## 確認する観点

正しさ、安全性、想定負荷での動作、テスト、性能、複雑さの順に確認する。
簡略化だけなど対象を絞られた場合はその範囲を守り、網羅的な品質確認とは報告しない。

| 観点 | 確認すること |
|---|---|
| 不具合 | 誤った結果、クラッシュ、空・ゼロ・末尾・丸め・時差の境界条件、呼び出し元と戻り値の不一致、同じ規則の適用漏れや食い違い |
| 安全性・データ保護 | インジェクション、不適切な乱数、秘密情報の露出、信頼境界の入力検証、認証・権限、データ漏えい、エラーの握りつぶし、書き込み順序、必要なトランザクションの欠落によるデータ損失 |
| 想定負荷 | 確認してから書く間の競合、各プロセスで重複する処理、増え続けるメモリやリスト、項目ごとのクエリ、大きな入力で件数の二乗に比例して増える処理（O(n²)）、共有すべき状態がプロセス内に閉じている問題 |
| テスト不足 | 分岐・反復、パーサー、金額、セキュリティ、データ書き込み、不具合修正、新しいスクリプトやアプリに、壊れると失敗する検証があるか。カバレッジの数値やテストの有無だけで判断しない |
| 性能 | 想定入力での大きな遅延、頻繁に通るループ内の重複処理、明示された応答時間の要件。測定で確認した性能低下とコードから予想する懸念、小さな改善案を区別する |
| 複雑さ | 下表の削除・再利用・置換・統合・分割によって、必要な動作を保ちつつ保守負担を減らせるか |

外部入力や他プロセス由来の値がコマンド実行・削除・上書き・認証付き操作へ届く場合は、
[trust-boundaries.md](trust-boundaries.md)で対象の認可、所有の根拠、確認後の競合を追う。
形式検証や監査ツールの成功だけで安全と判定しない。

## 小さくする候補

| 種別 | 探すもの |
|---|---|
| `delete` | 未使用と確認できたコード、不要な設定、依頼に含まれない将来機能 |
| `reuse` | 同じ責務を実装し直している処理、既存の関数や型に統合できる重複 |
| `stdlib` | 標準ライブラリの具体的な機能で置換できる手書き処理 |
| `native` | ブラウザー、OS、データベースなどの標準機能で置換できる処理や依存 |
| `yagni` | 現在の用途や境界では必要性を説明できない抽象化、ラッパー、拡張点 |
| `merge` | 同じ理由で一緒に変更すべき類似処理。見た目の類似だけでは統合しない |
| `split` | 無関係な責務が混ざり、理解や検証が難しい関数・型。責務で分け、行数だけを理由にヘルパーを増やさない |
| `shrink` | 同じ動作をより明瞭かつ小さく書ける処理 |

一つの実装や呼び出し元しかないことだけで抽象化を不要とは判断しない。

## 指摘の裏付け

- 大きな判断では、実装の入出力・状態変化・失敗経路を要件と対応付ける。理解できない箇所は調査対象として示し、読みにくさだけを不具合と断定しない。理由の残し方は、設計意図が不明な場合に[decision-evidence.md](decision-evidence.md)を読む。
- 実装とテストの期待値が同時に変わる場合は、要件や利用側の具体例で変更の妥当性を確かめる。新しい期待値で緑になったことだけでは、以前守っていた動作を捨てる根拠にならない。
- 各指摘に「この入力・状況で、この結果になる」という具体例を持つ。再度コードを読み、呼び出し元が存在するか、値が実際に空になり得るかなどを確認する。簡略化の指摘も、具体的な重複箇所や不要な処理と保守への影響を示す。好みや漠然とした懸念だけでは指摘しない。
- 未使用と判断する前に、対象ツリーの実装、テスト、fixture、設定、文字列・動的参照、外部利用を確認する。検索ヒットがないことだけでは削除を勧めない。
- `nwiizo-coding-style:`、`shortcut:`、`ponytail:` などで制限と見直す条件が明示されている場合は、現在の要件や想定負荷がその条件に達しているか確認する。条件内の意図的な制限は、それだけで不具合としない。コメントがあっても、要求された動作や安全性の欠落は免除しない。
- 修正案は原因を解消する最小限のものにする。移動・統合・削除・置換で入力検証、データ損失を防ぐエラー処理、安全性、アクセシビリティ、実機で必要な校正、性能・運用要件を失わせない。

各指摘には場所、そのコードの役割、問題が起きる具体例、最小の修正案、放置した場合の
影響を含める。報告形式は呼び出し元に合わせ、実行した検証と未確認事項を分ける。
指摘がない場合も確認範囲を示し、未実行のテストや本番動作まで合格扱いしない。
