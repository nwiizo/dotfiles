## 実装前の調査と変更

配置先は [SKILL.md](../SKILL.md)。

| 上流の確認項目 | 配置先・適用方法 |
|---|---|
| 依頼と関係するコードを読み、変更箇所を把握する | 「実装する前に読む」で入力から結果を追う |
| 呼び出し元、テスト、fixture、設定、exportまで変更を届ける | 同節で影響範囲と互換性を調べ、「小さくする判断」で関連修正を完了する |
| データ破壊・露出、壊れる呼び出し元を調べる | 「実装する前に読む」でデータ損失・漏えいと差分外の利用箇所を確認する |
| 不要な機能を増やさず、大まかな依頼でも中心の用途を満たす | 「実装の選び方」1。ユーザーが指定した機能は保つ |
| 既存コード、標準機能、導入済み依存、明瞭な1行、必要な実装の順に探す | 同節1〜7。既存部品を周囲と同じ使い方で再利用し、レイヤーを保つ |
| 不要な抽象化・ラッパー・型変換・設定・将来対応を増やさない | 「小さくする判断」。値をそのまま扱えるか確認し、現在必要な境界は保つ |
| 小さな差分でも端の条件を満たす。読みにくい短縮はしない | 「実装の選び方」の成立条件と「小さくする判断」で可読性・動作の同等性を確認する |
| コメントにはコードから分からない理由を書く | 「小さくする判断」で理由と制限を説明する |
| 不具合は呼び出し元を探し、共通原因を直す | 「実装する前に読む」。呼び出し元の意図的な違いは保つ |
| 移動・統合時も検証、データ損失防止、安全性、アクセシビリティ、実機の校正、要求された動作を保つ | 「小さくする判断」とreview-checksの「指摘の裏付け」 |
| 分岐・反復・パーサー・金額・セキュリティ・新規スクリプトやアプリの検証 | 「検証と完了」で壊れると失敗する検証を残す。単純な変更は対象に応じた確認にする |
| 既知の制限と見直す条件をコメントに残す | 「小さくする判断」。既存形式とプロジェクト指定の形式も尊重する |
| 見送り・未確認・リスクを伝える | 「検証と完了」。結果に関係する情報を示し、無関係な定型文は足さない |

## review・audit

共通の確認観点は [review-checks.md](review-checks.md)、対象選択・監査の進め方・報告は
[operations.md](operations.md) の `review` と `audit` に置く。独立した品質レビュアーも
同じ確認観点を参照する。

| 上流の確認項目 | 配置先・適用方法 |
|---|---|
| 指定差分・ブランチ・PR・ファイルを対象にする。変更がなければ直近コミット | `review` の対象選択。比較元と対象を明示し、新規ファイルも読む |
| 差分に加え呼び出し元・呼び出し先・テスト・READMEを読み、入力・保存・出力を追う | 「処理の流れと想定負荷」 |
| README・デプロイ設定から利用者数・プロセス数・入力規模を知る | 同節。根拠と仮定を区別し、根拠のない大規模化を求めない |
| 誤結果、クラッシュ、空・ゼロ・末尾・丸め・時差、利用側との不一致、規則の適用差 | 「確認する観点」の不具合 |
| インジェクション、乱数、秘密情報、信頼境界、データ損失、書き込み順序・トランザクション | 同表の安全性・データ保護。認証・権限と漏えいも確認する |
| 確認後の書き込み競合、プロセスごとの重複、増え続けるメモリ、項目ごとのクエリ、二乗の処理、共有状態 | 同表の想定負荷 |
| 危険な処理・不具合修正に、壊れると失敗する検証があるか | 同表のテスト不足。テスト数やカバレッジだけでは判定しない |
| 大きな遅延、頻繁なループ内の重複、時間要件と小さな高速化の区別 | 同表の性能。実測と推測を分ける |
| 削除、再利用、標準機能への置換、不要な抽象化、類似処理の統合、責務による分割 | 「小さくする候補」の `delete` / `reuse` / `stdlib` / `native` / `yagni` / `merge` / `split`。既存の `shrink` も維持する |
| 具体例を持ち、再読して裏付ける。未使用は設定・文字列・動的参照も探す | 「指摘の裏付け」。好みや未確認の懸念を指摘にしない |
| 意図的な制限は、想定負荷が見直す条件に達したかで判断する | 同節。明示された要件や安全性の欠落はコメントで免除しない |
| 原因を解消する最小限の修正案 | 同節。必要のない層・設定を増やさず、維持すべき動作を確認する |
| 変更の役割、優先順位、場所、問題、修正、放置した影響、判断、未確認事項 | 「報告」。番号付きの指摘、要修正・改善推奨・任意の分類を使う |
| 削減行数・依存数の根拠、指摘がない場合の報告 | 同節。見込みと適用済みの変更を分け、確認範囲を示す |
| 全体監査の構造把握、依存・入口・ビルド・デプロイ・テストの確認 | `audit` で主要経路を把握してから読む |
| ユーザー入力・金額・認証・書き込み・job・プロセス共有を優先する | `audit` で影響が大きい経路を深く読み、未確認領域を明示する |

## debt・gain・help

配置先は [operations.md](operations.md) の各操作。

| 上流の確認項目 | 配置先・適用方法 |
|---|---|
| `shortcut:`・旧`ponytail:`・指定マーカー、ignore設定、実際の制限コメントの識別 | `debt`。独自の `nwiizo-coding-style:` も収集し、説明文やキーボード操作のコメントを除く |
| 場所・制限・見直す条件・対応、条件なしの印、件数、変更者、保存範囲 | `debt`。`no-trigger` を付け、条件を推測しない。変更者と現在の担当者を区別する |
| ベンチマークのモデル・課題数・反復・集計方法、コード・出力トークン・費用・時間 | `gain`。2026-10-07の結果を固定リンクで参照する |
| 非公開検査の合格率、検証を残した割合、現在のrepoの効果と混同しない | `gain`。検査対象・生成時の実行制限・不合格例も含めて説明する |
| モード、停止、既定値、単発操作、状態を書き出さない | 本体の「モードと操作」と `help`。モードや設定の扱いはこのスキルの既存方式を維持する |

## ローカル方針を保つ箇所

確認する論点を取り込み、上流の行数・件数・出力書式は一律には強制しない。
テストを1件に制限せず、監査の20件上限で重要な指摘を落とさない。
実装が一つという理由だけで抽象化を消さず、必要な依存や検証も短さを理由に削らない。
`ultra` でも明示された要件を独断で外さず、修正まで頼まれていればレビューで止めない。

Ponytailのインストール、band・board、履歴取り込み、ホスト固有のフックや永続設定は
コードの確認項目とは別の機能であり、このスキルには組み込まない。
Rustの型・所有権・Edition・MSRV・構造診断は、このスキル独自の指針として維持する。
